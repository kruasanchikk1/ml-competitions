# RAG-пайплайн в Langflow: поиск по регулированию НПС (161-ФЗ)

Портфолио-кейс под вакансию "Промпт-инженер" (Langflow / RAG / LLMOps).
Рабочий RAG-пайплайн: чанкинг с overlap → эмбеддинги → двухэтапный поиск
(вектор + реранкинг) → фильтрация по метаданным → генерация ответа в
Langflow → трейсинг в Langfuse.

## Зачем этот кейс и как его читать

Я не позиционирую себя как ML/LLM-инженера — этот трек обычно требует
3+ года профильного опыта, которого у меня нет. Я аналитик, который
строит прикладные AI-инструменты: с LangGraph уже работал (Voice2Action:
FastAPI + LangGraph + YandexGPT + Whisper + RAG), с Langflow — нет, и этот
репозиторий закрывает именно этот пробел и даёт живой пример, а не
пересказ теории на собеседовании.

## Данные

Не банковские данные и не игрушечный `docs/example.pdf` — открытые статьи
Федерального закона 161-ФЗ "О национальной платежной системе"
(термины и определения, требования к правилам платёжной системы, защита
информации). Официальные тексты законов не защищены авторским правом
(п. 6 ст. 1259 ГК РФ), домен близок к банковскому. Подробности и ссылки
на источники — `data/SOURCES.md`.

## Архитектурные решения (и почему)

**Модель эмбеддингов — BGE-M3.** Открытая, мультиязычная (включая
русский), разворачивается локально без похода во внешнее облако — прямое
попадание в требования закрытого контура банка. Код специально не завязан
на одну модель: тот же интерфейс (`ingestion/embedders.py`) поддерживает
**Qwen3-Embedding-0.6B** — более новую мультиязычную модель Alibaba
сопоставимого размера, которая на момент написания часто обгоняет BGE-M3
на мультиязычных бенчмарках MTEB. Реального сравнения качества на этом
корпусе я не проводил (см. "Честно про ограничения" ниже) — но
архитектурно пайплайн готов к side-by-side между ними одной сменой
переменной окружения `EMBEDDING_BACKEND`.

**Чанкинг с overlap, не наивная фиксированная нарезка.**
`ingestion/chunk.py` режет текст по абзацам/пунктам статьи (не разрывая
определение или часть статьи посередине), упаковывает их в чанки
~900 символов, и каждый следующий чанк начинается с хвоста предыдущего.
На юридическом тексте это особенно важно: пункт 18 статьи 3 (определение
"электронных денежных средств") — одно предложение почти на 900 символов
с оговоркой-исключением в конце; фикс-сайз нарезка ровно посередине убила
бы половину смысла.

**Двухэтапный поиск.** top-100 кандидатов через косинусное расстояние
(дёшево, грубо) → реранкер (кросс-энкодер BGE reranker) пересчитывает
релевантность пары (вопрос, документ) точнее и сужает до top-3/5. Это
явно "система, которая построена, а не просто описана словами" — эффект
виден в `eval/results.json` (ниже).

**Фильтрация по метаданным до векторного поиска.** Каждый чанк несёт
метаданные из frontmatter документа (закон/глава/статья/источник) —
`retrieval/search.py` умеет фильтровать по ним в самом запросе к Qdrant,
а не постфактум. Дешевле: незачем считать косинусное расстояние с
точками, которые заведомо не подходят по статье.

**Langfuse для LLMOps.** Трейсинг цепочки (retrieval → prompt → LLM),
версионирование промпта, метрики токенов/стоимости/латентности — то, что
явно указано в требованиях вакансии как основа LLMOps-практики.

## Side-by-side: эффект реранкинга

`eval/run_sidebyside.py` прогоняет 10 тестовых вопросов по корпусу через
пайплайн дважды — с реранкингом и без — и считает accuracy@1 (попал ли
топ-1 результат по ожидаемым ключевым словам). Числа ниже получены на
**офлайн dev-бэкенде** (см. "Честно про ограничения") — сам факт, что
эффект реранкинга воспроизводится и измеряется автоматически, важнее
конкретных цифр:

```
Accuracy@1 без реранкинга:  40%  (4/10)
Accuracy@1 с реранкингом:   50%  (5/10)
```

Полная таблица по каждому вопросу — `eval/results.json` после запуска.
На реальных эмбеддингах (BGE-M3 + BGE reranker) абсолютные числа будут
заметно выше на обоих этапах — сравнение "с рериком / без" останется
воспроизводимым тем же скриптом.

## Честно про ограничения этого репозитория

Собирался в изолированной среде без доступа к Hugging Face (сетевая
политика блокировала huggingface.co), поэтому:

- Пайплайн **написан и протестирован end-to-end** (чанкинг → индексация
  → поиск → реранкинг → eval) на детерминированном офлайн-эмбеддере
  (`HashEmbedder` / `LexicalOverlapReranker` в `ingestion/embedders.py` и
  `retrieval/rerankers.py`) — bag-of-words с хэш-трюком, даёт настоящую
  косинусную близость по общим словам, но не является семантическим
  эмбеддингом.
- Реальные BGE-M3 / Qwen3-Embedding / BGE-reranker **не запускались** в
  среде сборки — веса скачаются автоматически при первом запуске на
  машине с доступом в интернет, простой сменой `EMBEDDING_BACKEND=bge-m3`
  в `.env`. Код к этому уже готов, менять ничего не нужно.
- `docker-compose.yml` проверен запуском (05.10.2026, Docker Desktop):
  `docker compose up -d` поднимает Langflow (UI на :7860, `/health` отвечает
  200) и Qdrant (:6333, коллекция `rag_knowledge_base` доступна). Langfuse
  подключается через `LANGFUSE_*` (облачный `cloud.langfuse.com` по
  умолчанию). Не проверялось: сборка флоу в UI и сквозной запрос с
  реальным LLM-ключом.

Это сознательный компромисс между "собрать реальную рабочую систему" и
"честно показать, что проверено, а что нет" — на мой взгляд, вторая часть
не менее важна на собеседовании про LLM-оценку.

## Быстрый старт

```bash
git clone <этот репозиторий>
cd langflow-rag-alfa
cp .env.example .env          # заполните ключи LLM при необходимости
docker compose up -d          # поднимет Langflow (7860) и Qdrant (6333); Langfuse по умолчанию облачный (cloud.langfuse.com)

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Индексация корпуса (первый запуск с bge-m3 скачает ~2.2 ГБ весов)
python -m ingestion.build_index --backend bge-m3 --qdrant http://localhost:6333

# Проверка поиска из консоли
python -m retrieval.search "какие требования к защите информации" --backend bge-m3 --rerank-backend bge

# Side-by-side eval
python -m eval.run_sidebyside --backend bge-m3 --rerank-backend bge
```

Дальше — сборка визуальной цепочки в Langflow UI, см.
`docs/LANGFLOW_SETUP.md`.

## Структура репозитория

```
data/
  raw/            markdown-документы корпуса (frontmatter = метаданные)
  SOURCES.md      источники и обоснование выбора данных
ingestion/
  chunk.py        чанкинг с overlap
  embedders.py    BGE-M3 / Qwen3-Embedding / офлайн hash-эмбеддер
  build_index.py  сборка индекса в Qdrant
retrieval/
  search.py       двухэтапный поиск + фильтрация по метаданным
  rerankers.py    BGE reranker (кросс-энкодер) / офлайн lexical-заглушка
eval/
  questions.json      10 тестовых вопросов по корпусу
  run_sidebyside.py   сравнение с реранкингом / без
docs/
  LANGFLOW_SETUP.md   пошаговая сборка флоу в Langflow UI
docker-compose.yml    Langflow + Qdrant (Langfuse: облако или отдельно)
```

## Питч для собеседования (кратко, STAR)

**Situation:** вакансия требует Langflow, RAG, side-by-side оценку и
LLMOps — с Langflow лично не работал, но есть смежный опыт (LangGraph) и
понимание RAG-теории.

**Task:** за ограниченное время собрать не ноутбук с демо, а рабочую,
задеплоенную через docker-compose систему, которую можно показать и
объяснить архитектурно.

**Action:** выбрал открытый, но тематически близкий к банку корпус
(161-ФЗ); реализовал чанкинг с overlap вместо наивной нарезки; двухэтапный
поиск с реранкингом и фильтрацией по метаданным; подключил Langfuse под
LLMOps-требование; написал side-by-side eval-скрипт, который численно
показывает эффект реранкинга, а не просто заявляет его на словах.

**Result:** рабочий пайплайн в репозитории, воспроизводимый одной
командой `docker compose up`, с честной документацией того, что
проверено в реальной среде, а что — архитектурно готово, но не
провалидировано вживую из-за сетевых ограничений среды сборки.
